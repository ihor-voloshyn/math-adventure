# 1. Назначение

Math Engine — независимый программный слой Math Adventure, отвечающий за математическую часть игры.

Он должен:

- хранить структуру математических навыков;
- знать зависимости между навыками;
- получать информацию о математических попытках ребёнка;
- предоставлять валидированные математические evidence для Mastery System;
- проверять математическую корректность Task Instance и результатов попыток;
- предоставлять Game Engine результат математического действия;
- работать независимо от конкретного игрового сценария.

Math Engine **не управляет игровым миром напрямую**.

---

# 2. Основной принцип

Архитектура должна разделять:

```text
МАТЕМАТИКА
     │
     ▼
Math Engine
     │
     ▼
Игровое действие
```

а не:

```text
Battle.java
 ├── сложение
 ├── вычитание
 ├── таблица умножения
 ├── проверка навыка
 └── определение сложности
```

Математические правила не должны быть распределены по игровым механикам.

# 4. Curriculum

Curriculum определяет **какие математические знания существуют в игре**.

Источник:

`05_MATH_CURRICULUM.md`

Curriculum содержит:

- области;
- навыки;
- поднавыки;
- описание навыков;
- допустимые уровни сложности;
- связи с другими навыками.

Curriculum не хранит состояние конкретного ребёнка.

---

# 5. Skill

Каждый математический навык является отдельной сущностью.

Пример:

```text
Skill:
    id: ADDITION_SINGLE_DIGIT
    domain: ADDITION
    name: Сложение однозначных чисел
```

Другой пример:

```text
Skill:
    id: UNKNOWN_ADDEND
    domain: ADDITION
    name: Неизвестное слагаемое
```

---

# 6. Уникальный идентификатор навыка

Каждый Skill должен иметь стабильный уникальный ID.

Пример:

```text

NUM_COUNT_BACKWARD
NUM_COMPARE
NUM_NUMBER_LINE
ADD_BASIC
ADD_CROSS_TEN
ADD_MULTI_DIGIT
ADD_UNKNOWN_ADDEND
SUB_BASIC

DIV_EXACT
DIV_REMAINDER
FRACTION_PART_OF_WHOLE
MONEY_CHANGE
TIME_DURATION
LOGIC_SEQUENCE
PREALGEBRA_UNKNOWN
```

ID не должен зависеть от языка интерфейса.

# 8. Skill Graph

Навыки образуют граф зависимостей.

Пример:

```text
NUMBERS
   │
   ├── ADD_BASIC
   │      │
   │      └── ADD_CROSS_TEN
   │
   └── SUB_BASIC
          │
          └── SUB_CROSS_TEN
```

Другой пример:

```text
ADD_BASIC
     │
     ▼
MUL_EQUAL_GROUPS
     │
     ▼
MUL_TABLE
     │
     ▼
DIV_EXACT
```

Фактический граф должен быть гораздо более детальным.

# 9. Типы зависимостей

В MVP достаточно двух основных типов:

### REQUIRED

Навык является необходимой предпосылкой.

```text
ADD_BASIC
   ↓ REQUIRED
ADD_CROSS_TEN
```

### RELATED

Навыки связаны, но один не является обязательным блокирующим prerequisite.

```text
MONEY
   ↔ RELATED
ADDITION
```

Архитектура должна позволять добавлять новые типы связей позднее.

---

# 10. Требование к графу

Для MVP основной граф зависимостей должен быть направленным и не содержать циклов prerequisite.

Недопустимо:

```text
A requires B
B requires C
C requires A
```

Такой цикл может заблокировать математическую прогрессию.

---

# 11. Состояние навыка ребёнка

Для каждого ребёнка хранится отдельное состояние каждого используемого навыка.

Минимальная модель:

```text
SkillState
    skillId
    mastery
    attempts
    correctAttempts
    lastAttemptAt
    lastCorrectAt
    consecutiveCorrect
    consecutiveErrors
```

---

# 12. Mastery

Mastery — оценка текущего состояния освоения конкретного навыка.

В MVP используется шкала:

```text
0–5
```

---

# 13. Значения Mastery

## 0 — Не изучен

Ребёнок:

- ещё не демонстрировал навык;
- либо данных недостаточно для оценки.

---

## 1 — Первичное знакомство

Ребёнок:

- начинает сталкиваться с навыком;
- может решить отдельные простые задачи;
- устойчивого понимания пока нет.

---

## 2 — Формируется

Ребёнок:

- уже понимает базовый принцип;
- иногда ошибается;
- требует повторения.

---

## 3 — Рабочее владение

Ребёнок:

- обычно решает задачи правильно;
- может применять навык в знакомых контекстах;
- ещё требует периодической проверки.

---

## 4 — Устойчивое владение

Ребёнок:

- стабильно решает задачи;
- справляется с разными представлениями;
- способен применять навык в различных игровых контекстах.

---

## 5 — Уверенное мастерство

Ребёнок:

- стабильно использует навык;
- сохраняет его при повторной проверке;
- справляется с вариациями задач;
- может использовать навык как основу для более сложных навыков.

---

# 14. Mastery не равно проценту правильных ответов

Mastery не должна рассчитываться как простое:

```text
correct / attempts
```

Например:

```text
10 правильных из 10
```

не обязательно означает полное мастерство.

Система должна учитывать:

- количество попыток;
- разнообразие задач;
- сложность;
- контекст;
- давность проверки;
- ошибки после предыдущего успеха;
- повторную проверку.

---

# 15. История попыток

Каждая математическая попытка должна иметь событие.

Минимальная структура:

```text
MathAttempt
    attemptId
    skillId
    taskId
    sessionId
    timestamp
    answerResult
    hintUsed
    difficulty
    contextType
```

---

# 16. Что НЕ требуется хранить как основной параметр

Для Math Engine не требуется использовать:

- скорость ответа как фактор награды;
- сложные психологические профили;
- предположения о типе личности ребёнка;
- отдельный рейтинг «быстрый/медленный ученик».

Система ориентирована прежде всего на математическое понимание и устойчивость навыка.

---

# 17. Ошибка

Ошибка должна фиксироваться как событие.

Пример:

```text
skill = ADD_CROSS_TEN
result = INCORRECT
```

Ошибка может привести к:

- снижению уверенности в текущем mastery;
- дополнительной проверке;
- упрощению следующего задания;
- повторению навыка.

Но:

**одна ошибка не должна автоматически обнулять Mastery.**

---

# 18. Правильный ответ

Правильный ответ увеличивает уверенность системы в навыке.

Однако:

```text
1 правильный ответ
≠
автоматический Mastery 5
```

После правильного ответа система может решить:

- продолжить текущую сложность;
- проверить навык в другом контексте;
- перейти к связанному навыку;
- запланировать повторную проверку.

---

# 19. Подсказки

Использование подсказки фиксируется.

Например:

```text
hintUsed = false
```

или:

```text
hintUsed = true
hintLevel = 1
```

Подсказка не должна уменьшать игровую награду в MVP.

Она используется прежде всего как сигнал о том, что ребёнку потребовалась помощь.

---

# 20. Пропуск

Если ребёнок пропустил математическую задачу:

```text
result = SKIPPED
```

Навык не считается освоенным или неосвоенным только на основании пропуска.

Adaptive Engine может вернуть этот навык позднее.

---

# 21. Повторная проверка

После достижения высокого Mastery навык должен периодически проверяться снова.

Пример:

```text
Mastery 4
      ↓
другая игровая ситуация
      ↓
успешно
      ↓
Mastery сохраняется
```

Если ребёнок начинает ошибаться:

```text
Mastery 4
      ↓
ошибка
      ↓
дополнительная проверка
      ↓
Mastery может снизиться
```

Система должна отличать единичную ошибку от устойчивой потери навыка.

---

# 22. Забывание

В MVP не требуется сложная математическая модель забывания.

Однако архитектура должна позволять в будущем учитывать:

- время с последней проверки;
- стабильность навыка;
- историю повторных проверок.

Таким образом, Mastery может стать динамической характеристикой, а не постоянным флагом.

---

# 23. Диагностический режим

Math Engine должен поддерживать диагностические задания.

Диагностика используется для:

- первоначальной оценки;
- проверки предположительно освоенных навыков;
- определения пробелов;
- проверки prerequisites.

Диагностика может использовать чистое математическое представление без игрового контекста.

---

# 24. Cold Start

Для нового ребёнка Math Engine не знает его уровень.

Начальное состояние:

```text
Mastery = UNKNOWN
```

или эквивалентное внутреннее состояние.

Система постепенно получает информацию через:

- диагностические задания;
- первые игровые задания;
- наблюдение за результатами.

---

# 25. Определение доступных навыков

Skill считается потенциально доступным, если:

1. он существует в Curriculum;
2. его обязательные prerequisites выполнены;
3. ребёнок ещё не достиг требуемого устойчивого Mastery;
4. Adaptive Engine считает его подходящим для текущего момента.

Упрощённо:

```text
EligibleSkill =
    Curriculum
    +
    Prerequisites
    +
    LearnerState
    +
    AdaptivePolicy
```

---

# 26. Mathematical Progress Gate

Главный математический прогресс определяется Mastery.

Пример:

```text
ADD_BASIC
Mastery 4
      ↓
ADD_CROSS_TEN
становится доступным
```

Но конкретный порог не должен быть жёстко зашит в Game Engine.

Порог является параметром Math/Adaptive Engine.

---

# 27. Связь с RPG

Game Engine может спросить:

```text
CanUseMathSkill(skillId)?
```

Math Engine возвращает результат.

Например:

```text
AVAILABLE
BLOCKED
REQUIRES_REVIEW
```

Game Engine не должен сам вычислять Mastery.

---

# 28. Интерфейс Math Engine

Концептуальный API:

```text
getSkill(skillId)

getSkillState(playerId, skillId)

getAvailableSkills(playerId)

generateTask(context)

evaluateAttempt(attempt)

getMastery(playerId, skillId)

getProgress(playerId)

checkPrerequisites(playerId, skillId)
```

Фактический API будет определён на этапе технической архитектуры.

---

# 29. Контекст задания

При запросе задания Game Engine передаёт контекст.

Например:

```text
TaskContext
    playerId
    gameMode
    actionType
    location
    questId
    enemyType
    allowedSkills
    rewardContext
```

Пример:

```text
gameMode = BATTLE
actionType = ATTACK
enemyType = GOBLIN
```

Math Engine сам выбирает подходящий математический навык.

---

# 30. Math Engine не выбирает игровой сюжет

Math Engine может определить:

> «ребёнку сейчас подходит сложение с переходом через десяток».

Но он не должен решать:

> «ребёнок должен пойти в лес».

Выбор игрового сценария относится к Game Engine.

---

# 31. Результат математического действия

Math Engine возвращает структурированный результат.

Пример:

```text
MathResult
    correct
    skillId
    masteryBefore [legacy/read-only]
    masteryAfter [legacy/read-only]
    hintUsed
    confidence
```

Game Engine преобразует этот результат в игровое действие.

Например:

```text
correct = true
        ↓
ATTACK_SUCCESS
```

или:

```text
correct = false
        ↓
TURN_LOST
```

---

# 32. Разделение ответственности

## Math Engine отвечает за

- математические навыки;
- Skill Graph;
- Mastery;
- оценку математических попыток;
- математическую сложность;
- математическую последовательность;
- диагностику;
- выбор подходящего математического содержания.

## Game Engine отвечает за

- персонажа;
- мир;
- бой;
- NPC;
- квест;
- инвентарь;
- предметы;
- награды;
- движение;
- визуальное представление.

# 35. Один навык — много игровых контекстов

Один Skill не должен быть связан только с одной механикой.

Например:

```text
ADD_BASIC
 ├── Battle
 ├── Shop
 ├── Quest
 ├── Exploration
 ├── Puzzle
 └── Construction
```

Это является важным механизмом проверки реального понимания.

---

# 36. Один игровой контекст — много навыков

Например, Battle может использовать:

```text
ADD_BASIC
SUB_BASIC
MUL_BASIC
DIV_BASIC
LOGIC_SEQUENCE
UNKNOWN_VALUE
WORD_PROBLEM
```

Конкретный навык выбирается Adaptive Engine.

---

# 37. Динамический выбор сложности

Math Engine должен поддерживать несколько уровней сложности одного навыка.

Например:

```text
ADD_BASIC

Level 1
3 + 4

Level 2
7 + 8

Level 3
17 + 6

Level 4
37 + 28

Level 5
125 + 78
```

Конкретные диапазоны являются параметрами Task Generator.

---

# 38. Сложность ≠ новый навык

Важно различать:

```text
Skill
```

и:

```text
Difficulty
```

Например:

```text
ADD_BASIC
Difficulty 1
Difficulty 2
Difficulty 3
```

Это один и тот же математический навык разной сложности.

---

# 39. Контекст ≠ математический навык

Также необходимо различать:

```text
Skill:
ADDITION
```

и:

```text
Context:
BATTLE
SHOP
QUEST
PUZZLE
```

Это позволяет использовать один математический навык в разных частях игры.

---

# 40. Защита от шаблонного запоминания

Math Engine должен избегать чрезмерного повторения одной и той же формы задачи.

Например, вместо:

```text
7 + 8 = ?
7 + 8 = ?
7 + 8 = ?
```

система должна использовать вариации:

```text
7 + 8 = ?

У героя 7 монет.
Он получил ещё 8.
Сколько стало?

На полке 7 зелий.
Принесли ещё 8.
Сколько теперь?

Какое число нужно добавить к 7,
чтобы получить 15?
```

Математический навык один, представления разные.

---

# 41. Несколько правильных способов

Если математическая задача допускает несколько корректных способов решения, Math Engine должен ориентироваться на математически правильный результат, а не требовать единственный внутренний алгоритм.

В MVP не требуется глубокий анализ каждого шага решения.

---

# 42. Пошаговое решение

Math Engine MVP не обязан анализировать каждый шаг вычисления.

Основная оценка:

```text
итоговый математический результат
```

Пошаговый анализ может быть добавлен позднее.

---

# 43. Обработка повторяющихся ошибок

Если ребёнок неоднократно ошибается:

```text
Error
   ↓
Error
   ↓
Error
```

Adaptive Engine может:

- уменьшить сложность;
- сменить представление;
- вернуться к prerequisite;
- дать подсказку;
- предложить другой контекст;
- временно отложить навык.

Math Engine не должен автоматически считать ребёнка неспособным освоить навык.

---

# 44. Обработка серии правильных ответов

Если ребёнок демонстрирует устойчивую серию:

```text
Correct
Correct
Correct
Correct
```

Adaptive Engine может:

- увеличить сложность;
- сменить контекст;
- проверить соседний навык;
- перейти к следующему prerequisite-зависимому навыку.

---

# 45. Правило перехода

Переход на следующий уровень не должен зависеть только от количества правильных ответов подряд.

Необходимо учитывать:

```text
точность
+
разнообразие
+
сложность
+
контекст
+
повторная проверка
```

---

# 46. Награда и Mastery

Math Engine может сообщить Game Engine:

```text
masteryImproved = true
```

Game Engine может использовать это для:

- открытия контента;
- выдачи игровой награды;
- изменения доступных возможностей.

Однако Math Engine не должен напрямую изменять:

- Coins;
- Inventory;
- RPG XP;
- предметы;
- характеристики персонажа.

---

# 47. Атомарность

Критическая операция математического результата должна обрабатываться согласованно.

Например:

```text
Task Completed
      ↓
Mastery Update
      ↓
Game Reward
```

Не должно возникать состояния:

```text
награда получена
но математическая попытка не сохранена
```

или:

```text
Mastery увеличен
но результат задания потерян
```

Система сохранения должна обеспечивать согласованность критических операций.

---

# 48. Offline-first

Math Engine должен работать без постоянного подключения к серверу.

В MVP:

```text
Math Engine
     ↓
Local State
```

Интернет не должен требоваться для:

- решения математических задач;
- обновления Mastery;
- прохождения уровней;
- использования основного математического контента.

---

# 49. Будущий сервер

Архитектура должна позволять в будущем:

```text
Client Math State
       ↓
Sync
       ↓
Server
       ↓
Authoritative State
```

Сервер в будущем должен стать источником истины для защищённого прогресса и наград.

При этом клиент должен оставаться способным работать офлайн.

---

# 50. Защита от изменения локального прогресса

Math Engine не должен предполагать, что локальное состояние является полностью доверенным.

В будущей серверной архитектуре необходимо предусмотреть:

- проверку математических событий;
- синхронизацию попыток;
- проверку последовательности событий;
- защиту наград;
- предотвращение подделки Mastery.

---

# 51. Родительский уровень

Math Engine должен предоставлять данные для родительского интерфейса.

Например:

```text
Сложение       █████████░  4/5
Вычитание      ████████░░  3/5
Умножение      ██████░░░░  2/5
Деление        ████░░░░░░  1/5
```

Но ребёнку не обязательно показывать технические значения Mastery 0–5.

Для ребёнка используется упрощённое игровое представление прогресса.

---

# 52. Родительская аналитика

В будущем Parent Dashboard может показывать:

- освоенные навыки;
- навыки в процессе освоения;
- проблемные области;
- динамику;
- последние ошибки;
- рекомендации для повторения.

Сложные технические параметры должны оставаться внутренними.

---

# 53. Локализация

Math Engine не должен хранить математические задания только в виде готового текста.

Предпочтительная структура:

```text
Task Definition
    ↓
Parameters
    ↓
Localized Renderer
```

Например:

```text
operation = ADD
a = 7
b = 8
```

А текст формируется отдельно.

Это позволяет поддерживать:

- русский;
- украинский;
- польский;
- английский;
- другие языки в будущем.

---

# 54. Независимость от языка

Skill ID:

```text
ADD_CROSS_TEN
```

остаётся одинаковым для всех языков.

Название:

```text
Русский: Сложение с переходом через десяток
Українська: Додавання з переходом через десяток
Polski: Dodawanie z przekroczeniem progu dziesięciu
English: Addition across ten
```

изменяется только на уровне локализации.

---

# 55. Независимость от валюты

Money Skills должны поддерживать локальные валюты.

Например:

```text
PLN
UAH
EUR
```

Математический навык остаётся тем же:

```text
MONEY_CHANGE
```

---

# 56. Независимость от игрового мира

Math Engine не должен знать конкретные координаты:

```text
x = 125
y = 20
z = 81
```

или конкретную модель:

```text
Goblin_03
```

Он получает абстрактный игровой контекст.

---

# 57. Основной цикл Math Engine

```text
1. Получить игровой контекст
        ↓
2. Определить допустимые навыки
        ↓
3. Проверить Skill Graph
        ↓
4. Получить Skill State
        ↓
5. Adaptive Engine выбирает Skill
        ↓
6. Определяется Difficulty
        ↓
7. Task Generator создаёт задачу
        ↓
8. Ребёнок отвечает
        ↓
9. Evaluate Attempt
        ↓
10. Обновляется Mastery
        ↓
11. Результат сохраняется
        ↓
12. Game Engine получает MathResult
```

---

# 58. Основной принцип отказоустойчивости

Если Math Engine временно не может определить идеальное следующее задание, система должна выбрать безопасный fallback.

Например:

```text
Adaptive decision unavailable
        ↓
использовать известный подходящий Skill
        ↓
сгенерировать безопасную задачу
```

Игра не должна ломаться из-за невозможности выполнить сложную адаптивную оптимизацию.

---

# 59. MVP и будущие модели

В MVP не требуется сразу использовать:

- Deep Knowledge Tracing;
- нейронную сеть;
- Reinforcement Learning;
- сложную IRT-модель;
- сложный ML-пайплайн.

Архитектура должна позволять добавить такие модели позднее.

Первоначальная реализация должна быть:

- прозрачной;
- тестируемой;
- детерминированной там, где это необходимо;
- пригодной для отладки;
- понятной разработчикам и QA.

---

# 60. Почему сначала Rule-Based

На первом этапе важно обеспечить:

```text
корректный Skill Graph
+
качественные задания
+
корректное состояние Mastery
+
правильный Adaptive Flow
```

Только после накопления реальных данных можно обоснованно усложнять математическую модель.

---

# 61. Тестируемость

Каждый компонент должен быть тестируем отдельно.

Минимально:

```text
Curriculum Tests
Skill Graph Tests
Mastery Tests
Task Selection Tests
Attempt Evaluation Tests
Prerequisite Tests
Localization Tests
Persistence Tests
```

# 69. Граница между Math Engine и Adaptive Engine

В проекте эти понятия связаны, но не идентичны.

### Math Engine

Отвечает за:

> **Что такое математика и как оценить математический результат?**

### Adaptive Engine

Отвечает за:

> **Что конкретному ребёнку дать следующим и почему?**

Упрощённо:

```text
Curriculum
    ↓
Math Engine
    ↓
Skill / Mastery
    ↓
Adaptive Engine
    ↓
Next Task
```

# 70. Граница между Math Engine и Task Generator

### Math Engine

Определяет:

```text
какой Skill
какая Difficulty
какие ограничения
```

### Task Generator

Определяет:

```text
конкретные числа
конкретный вопрос
конкретные варианты ответа
конкретный математический сценарий
```

# 71. Главный принцип архитектуры

Math Engine должен быть построен так, чтобы его можно было использовать независимо от того, где ребёнок находится:

```text
в бою
в магазине
в лесу
в деревне
в замке
в подземелье
в квесте
в головоломке
```

Игровой мир меняет **контекст математики**, но не должен менять саму математическую модель.

# 73. Статус документа

Главное правило:

> **Curriculum определяет математический мир. Math Engine понимает состояние знаний ребёнка. Adaptive Engine выбирает следующий математический шаг. Task Generator превращает этот шаг в конкретное задание. Game Engine превращает математический результат в игровое действие.**

## Reconciliation override

Mastery calculation and Mastery updates are owned exclusively by `08_MASTERY_SYSTEM.md`. Math Engine validates mathematical truth and produces validated attempt evidence; it does not mutate Mastery. Skill selection and pedagogical next-step selection are owned by Adaptive Engine. Task instantiation is owned by Task Generator.


## Reconciliation boundary

`08_MASTERY_SYSTEM.md` является единственным владельцем расчёта и изменения Mastery. Math Engine не изменяет Mastery. `09_ADAPTIVE_ENGINE.md` выбирает следующий педагогический шаг, Skill/Mode/Difficulty в пределах ограничений. `07_TASK_GENERATOR.md` создаёт конкретный Task Instance.
